# Security Guide

**Version**: 2.0  
**Last Updated**: April 24, 2026  
**Classification**: Internal Use Only  
**Audience**: Security team, DevOps, Platform Engineers  

## Executive Summary

The Paperclip platform implements defense-in-depth security with zero-trust principles. This guide documents authentication, authorization, secrets management, data protection, and compliance procedures.

## Security Architecture

### Zero-Trust Model

All access requests are authenticated and authorized, regardless of source:
- Every request requires valid credentials
- Every service validates credentials independently
- Principle of least privilege enforced throughout
- All actions logged and auditable

### Defense-in-Depth Layers

```
┌─ External (User) ─────────────────────────────┐
│                                               │
│  1. TLS/SSL Encryption (Transport Layer)      │
│     - All traffic over HTTPS (Caddy)          │
│     - TLS 1.3 minimum                         │
│     - Certificate pinning for critical paths  │
│                                               │
│  2. Authentication Layer (OAuth2-Proxy)       │
│     - OAuth2/OIDC for user identity           │
│     - MFA enforcement for admin users         │
│     - JWT tokens with short expiry            │
│                                               │
│  3. Authorization Layer (OPA)                 │
│     - Attribute-Based Access Control (ABAC)  │
│     - Fine-grained permission checks          │
│     - Resource-level access policies          │
│                                               │
│  4. Application Layer (API Gateway)           │
│     - Rate limiting and DDoS protection       │
│     - Request validation and sanitization     │
│     - Input validation on all endpoints       │
│                                               │
│  5. Data Layer (PostgreSQL)                   │
│     - Row-level security (RLS) policies       │
│     - Encryption at rest                      │
│     - Field-level encryption for sensitive    │
│       data (SSNs, credit cards, API keys)     │
│                                               │
└───────────────────────────────────────────────┘
```

## Authentication

### OAuth2/OIDC Integration

#### Supported Providers

1. **GitHub** (Primary)
   - Scopes: `user:email`, `read:org`
   - Token Rotation: Every 24 hours
   - Fallback: Allowed if primary fails

2. **Google** (Secondary)
   - Scopes: `email`, `profile`
   - Enterprise SSO: Workspace integration
   - Conditional Access: Location-based policies

3. **Azure AD** (Optional)
   - Enterprise: Conditional, available on request
   - Scopes: `openid`, `profile`, `email`
   - Integration: Microsoft 365 environment

#### Implementation Details

```bash
# OAuth2-Proxy Configuration
OAUTH2_PROXY_PROVIDER=github
OAUTH2_PROXY_CLIENT_ID=${GITHUB_OAUTH_CLIENT_ID}  # Via Vault
OAUTH2_PROXY_CLIENT_SECRET=${GITHUB_OAUTH_SECRET}  # Via Vault
OAUTH2_PROXY_REDIRECT_URL=https://kushnir.cloud/oauth2/callback
OAUTH2_PROXY_SCOPE="user:email read:org"
OAUTH2_PROXY_TOKEN_VALIDATION=true
OAUTH2_PROXY_SKIP_PROVIDER_BUTTON=false
OAUTH2_PROXY_PASS_ACCESS_TOKEN=false  # Never expose token to app
OAUTH2_PROXY_PASS_USER_HEADERS=true   # Pass user info
```

#### Token Management

**Token Issuance**:
- JWT tokens generated by OAuth2-Proxy
- Expiry: 1 hour (short-lived)
- Refresh tokens: 30 days (long-lived)

**Token Storage**:
- Never stored in cookies (localStorage is vulnerable)
- Stored in secure, HttpOnly cookies (CSRF-protected)
- SameSite=Lax enforced

**Token Revocation**:
- Supported via GitHub Apps token revocation
- Immediate effect on next request
- User logout triggers revocation

### Multi-Factor Authentication (MFA)

#### MFA Requirements

- **Admin Users**: Required
- **Regular Users**: Recommended
- **Service Accounts**: Not applicable (use API keys)

#### MFA Methods

1. **TOTP** (Time-based One-Time Password)
   - Google Authenticator, Authy, Microsoft Authenticator
   - 30-second window, 6 digits
   - Backup codes provided (10 per user)

2. **GitHub Built-in MFA**
   - Enabled via GitHub account settings
   - TOTP or SMS-based
   - Enforced during OAuth2 flow

#### Implementation

```bash
# In OAuth2-Proxy config
OAUTH2_PROXY_SKIP_JWT_BEARER_TOKEN=false
OAUTH2_PROXY_PROVIDER_DISPLAY_NAME="GitHub (MFA Required)"

# Application-level MFA check
function require_mfa(user_id) {
  const mfa_enabled = query('SELECT mfa_enabled FROM users WHERE id = ?', user_id);
  return mfa_enabled === true;
}
```

## Authorization

### Role-Based Access Control (RBAC)

#### Roles

| Role | Capabilities | Assignment |
|------|-------------|-----------|
| Admin | All operations, user management, system config | Manual, GSM-verified |
| Owner | Project owner, full access to owned resources | Auto-assigned on creation |
| Collaborator | Modify shared resources, limited access | Invite-based |
| Viewer | Read-only access | Invite-based |
| Guest | Limited public resources | No assignment needed |

#### Role Hierarchy

```
Admin (superuser)
  ├─ Owner (project-specific)
  │   ├─ Collaborator
  │   │   └─ Viewer
  │   └─ Guest (public only)
  └─ System Admin (infrastructure)
```

### Attribute-Based Access Control (ABAC)

#### OPA Policies

All access decisions delegated to OPA (Open Policy Agent):

```rego
# Example: Allow only project members to edit issue
allow_edit_issue {
    input.action == "issue.edit"
    issue := data.issues[input.issue_id]
    user_id := input.user_id
    
    # User must be project member
    is_member(issue.project_id, user_id)
    
    # User must have edit permission
    has_permission(user_id, issue.project_id, "issue.edit")
}

is_member(project_id, user_id) {
    project_member := data.project_members[_]
    project_member.project_id == project_id
    project_member.user_id == user_id
}

has_permission(user_id, project_id, permission) {
    role := get_user_role(user_id, project_id)
    role_permissions[role][_] == permission
}
```

#### Enforcement Points

1. **API Gateway**: Blocks unauthorized requests before app
2. **Application Layer**: Additional checks in business logic
3. **Database Layer**: Row-level security (RLS) prevents data leakage
4. **Audit Log**: All denials logged for investigation

## Secrets Management

### Storage Architecture

#### Hierarchy

```
Development: .env files (local only, .gitignored)
Staging: Google Secret Manager (GSM)
Production: Vault + GSM backup
```

#### Vault Integration

**Vault Server**:
- URL: `https://vault.kushnir.cloud:8200`
- Auth: Kubernetes service account (production)
- Auth: User token with TTL (development)

**Secret Paths**:
```
secret/data/database/      # Database credentials
secret/data/api-keys/      # Third-party API keys
secret/data/oauth2/        # OAuth2 client secrets
secret/data/certificates/  # TLS certificates
secret/data/slack-webhook/ # Integration tokens
```

**Access Control**:
- All access logged
- Separate policies per environment
- Automatic rotation every 90 days

### Credential Management

#### Database Credentials

**Security**:
- Never hardcoded in application code
- Stored in Vault with auto-rotation
- Least privilege: app user has only SELECT/INSERT/UPDATE (no DROP)
- Connection pooling via HikariCP with credential refresh

**Rotation Process**:
```bash
# Vault automatically rotates every 90 days
# Manual rotation (if needed):
vault write -f database/rotate-root/postgres
```

#### API Keys

**GitHub Token**:
- Type: GitHub App Personal Access Token (fine-grained)
- Scopes: issues, pull_requests, repository contents (read-only where possible)
- Expiry: 365 days (with manual rotation every 90 days)
- Storage: Vault

**Slack Webhook**:
- Type: Incoming Webhook
- Channels: #alerts, #deployments
- Rotation: Every 180 days
- Disabling: Instant via Slack workspace settings

#### OAuth2 Secrets

**Client Secrets**:
- Never exposed in logs or error messages
- Stored in Vault with separate read/write policies
- Rotated every 180 days
- Immediately revoked if leaked (detected via scanning)

### Secret Scanning

#### Tools

1. **git-secrets**: Pre-commit hook
   ```bash
   git secrets --install
   git secrets --add '<pattern-for-api-key>'
   ```

2. **TruffleHog**: Repository scanning
   ```bash
   trufflehog git https://github.com/kushin77/code-server.git
   ```

3. **GitHub Secret Scanning**:
   - Enabled by default
   - Alerts on push
   - Automatic token revocation for known patterns

#### Response Plan

1. **Detection**: Alert triggered
2. **Quarantine**: Credential immediately invalidated
3. **Notification**: Team alerted within 5 minutes
4. **Investigation**: Determine exposure scope
5. **Remediation**: Rotate all related secrets
6. **Communication**: User/system owner notified

## Data Protection

### Encryption at Rest

#### Database

**PostgreSQL Encryption**:
- Filesystem encryption: LUKS (Linux Unified Key Setup)
- Encryption key: Stored in HSM (Hardware Security Module)
- Key rotation: Every 365 days
- Backup encryption: AES-256-CBC

**Sensitive Fields**:
```sql
-- Encrypted columns use pgcrypto
CREATE TABLE users (
    id UUID PRIMARY KEY,
    email TEXT,
    ssn TEXT ENCRYPTED WITH pgcrypto,  -- Encrypted
    phone TEXT ENCRYPTED WITH pgcrypto, -- Encrypted
    api_key TEXT ENCRYPTED WITH pgcrypto -- Encrypted
);

-- Example: Store encrypted value
INSERT INTO users VALUES (
    '...',
    'user@example.com',
    pgp_sym_encrypt('123-45-6789', 'encryption_key'),
    pgp_sym_encrypt('+1-555-1234', 'encryption_key'),
    pgp_sym_encrypt('sk_prod_...', 'encryption_key')
);
```

### Encryption in Transit

#### TLS Configuration

**Caddy Reverse Proxy**:
```
kushnir.cloud {
    tls {
        protocols tls1.3    # TLS 1.3 minimum
        ciphers ECDHE-ECDSA-AES256-GCM-SHA384
    }
    # HSTS: 1 year
    header Strict-Transport-Security "max-age=31536000; includeSubDomains"
}
```

**Service-to-Service**:
- All inter-service communication over TLS
- Certificate pinning for critical services
- Mutual TLS (mTLS) for service authentication

#### HSTS & Security Headers

```
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
X-XSS-Protection: 1; mode=block
Content-Security-Policy: default-src 'self'
Referrer-Policy: no-referrer
```

## Compliance

### GDPR Compliance

#### Data Subject Rights

1. **Right to Access**: `/api/users/me/data` exports user data
2. **Right to Deletion**: `/api/users/me/delete` triggers GDPR deletion
   - All personal data deleted within 30 days
   - Backups purged within 90 days
3. **Right to Portability**: Export user data in JSON format
4. **Right to Object**: Withdraw consent at any time

#### Data Retention

| Data Type | Retention | Reason |
|-----------|-----------|--------|
| User account | Duration of use + 30 days | Legal hold |
| Activity logs | 90 days | Audit trail |
| Deleted data | Purged | GDPR requirement |
| Backups | 7 days | Disaster recovery |

#### Privacy Policy

- Published at: `https://kushnir.cloud/privacy`
- Updated: Quarterly or on material change
- Consent: Implicit on signup, explicit opt-in for marketing

### SOC 2 Type II

#### Control Areas

1. **Security**: 
   - Vulnerability scanning (monthly)
   - Penetration testing (quarterly)
   - Security team reviews (weekly)

2. **Availability**:
   - 99.9% uptime SLA
   - Automated failover < 5 seconds
   - Backup RTO: 15 minutes

3. **Processing Integrity**:
   - Audit logging (all changes)
   - Data validation (input/output)

4. **Confidentiality**:

## Incident Response

### Security Incident Classifications

| Level | Example | Response Time | Escalation |
|-------|---------|---------------|------------|
| Critical | Data breach, RCE | 15 min | CEO, Legal |
| High | Unauthorized access, DDoS | 1 hour | CISO, Security team |
| Medium | Configuration error | 4 hours | DevOps, Security |
| Low | Outdated dependency | 7 days | Engineering team |

### Incident Response Procedure

1. **Detection**:
   - Automated alerts (monitoring)
   - Manual reports (users, security team)

2. **Assessment** (within 30 min):
   - Scope and impact analysis
   - Affected systems and data
   - Classification (critical/high/medium/low)

3. **Containment**:
   - Isolate affected systems
   - Revoke compromised credentials
   - Block attacker IP ranges

4. **Eradication**:
   - Patch vulnerabilities
   - Rebuild systems from clean snapshots
   - Verify no persistence mechanisms

5. **Recovery**:
   - Restore data from backups
   - Bring systems online
   - Verify functionality

6. **Post-Incident**:
   - Root cause analysis
   - Preventive measures
   - Incident report (within 7 days)
   - Quarterly trend analysis
